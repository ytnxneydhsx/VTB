# 音视频同步层设计

## 为什么需要这一层

当前视频帧经过 RGA 和 MPP 后直接交给 `OutputManager`。后续音频链包含采集、
语音处理和音频编码，处理完成时间会晚于相同媒体时刻的视频包。若两个生产线程直接
调用 `OutputManager::publish()`，出口队列只保留调用顺序，无法表达等待音频的实时
策略。

同步层解决正确性问题：保留采集时刻产生的 PTS/DTS，在有限窗口内等待处理后的音频，
按全局 DTS 顺序把两路包交给输出层。同步层增加的缓存时长属于端到端延迟，需要通过
指标明确观察。

## 已有协议和项目职责

H.264、Opus/AAC、RTSP/RTP 和 FFmpeg 的交织复用均使用现有实现。`RtspOutput`
继续调用 `av_interleaved_write_frame()` 完成最终复用与发送。本项目不定义新的网络
同步协议。

FFmpeg 根据调用方提供的时间戳交织数据。它无法推断 ALSA 采集时刻、语音模型的
算法延迟、两路时钟是否同源，以及处理结果超过实时期限后应当丢弃还是继续等待。
`AvSynchronizer` 只补充这些项目内策略，不负责编解码、重采样、time-stretch、
静音生成或网络发送。

## 数据路径

```text
主进程 CLOCK_MONOTONIC
├─ 视频帧时刻 → Godot → RGA → MPP H.264 ───────┐
│                                               │
└─ ALSA 首样本时刻 → 语音处理 → Opus/AAC ──────┤
                                                v
                                         AvSynchronizer
                                                |
                                                v
                                         OutputManager
                                                |
                                                v
                                     RtspOutput / UVC / UAC2
```

语音处理完成时刻表示包已经可用，不替换音频采集 PTS。算法存在 lookahead、裁剪或
输出长度变化时，音频处理器必须提供输入样本到输出样本的时间映射。

## 首版策略

- 同步器接受固定的一路视频和一路音频，两路时间戳均为 `CLOCK_MONOTONIC` 纳秒；
- 每路 DTS 必须单调不减；相同 DTS 时稳定地先释放视频；
- 两路队列都有数据时选择最小 DTS；仅一路有数据时等待另一条流；
- 等待超过 `max_wait` 后强制释放，随后丢弃落后于全局 DTS 的迟到包；
- 迟到音频恢复时标记 discontinuity；迟到视频等待关键帧后标记 discontinuity；
- 每路队列容量固定。容量耗尽会拒绝新包并终止当前同步会话，避免无界内存和静默破坏预测链；
- 一路显式结束后，另一条流可以继续排空；两路结束时按 DTS 排空全部队列；
- sink 回调必须快速且不可进行网络 I/O。预期 sink 为 `OutputManager::publish()`；
- sink 异常会进入终止失败状态，调用方应停止当前媒体会话并重新创建同步器。

首版没有主动修改 PTS，也没有通过重复视频、补静音或重采样修正长期时钟漂移。只有
实测确认 ALSA 设备时钟与主进程单调时钟存在持续漂移后，再设计慢速重采样或视频
丢帧策略。

## 更简单的方案及边界

直接将音视频包交给 FFmpeg 可以完成普通文件或延迟不敏感场景的交织。当前语音处理
具有额外延迟，产品还需要较短且明确的等待上限、迟到包统计和关键帧恢复，因此增加
一个进程内同步器。它不会形成新进程、网络跳数或持久化状态。

## 验证指标

- 视频和音频队列深度；
- 接收、释放、迟到和拒绝包数；
- 超时强制释放次数；
- sink 错误次数；
- 最后释放 DTS；
- 接入真实音频后增加音频处理 P50/P95/P99、视频等待时长和输出端 A/V PTS 差。

单元测试覆盖处理后音频晚到、全局 DTS 排序、最大等待、迟到音频、视频关键帧恢复、
队列上限、非法流、单流 DTS 回退和 sink 失败。真实 RTSP/WebRTC 验证需要在音频采集
与编码链接入后单独执行。
